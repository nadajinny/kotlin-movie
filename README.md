## 구현 전략
### 1. 계층 분리
- 기존 도메인, 할인 정책, JDBC 영속화 로직은 유지한다.
- HTTP 요청/응답 형식은 `api` 패키지의 DTO와 컨트롤러에서만 다룬다.
- HTTP 계층은 입력 파싱과 응답 직렬화만 담당하고, 실제 비즈니스 규칙은 기존 도메인 객체를 사용한다.

### 2. 상영 ID 전략
- 도메인 객체에는 상영 ID 필드를 추가하지 않는다.
- `MovieTheater`를 기준으로 영화 순서와 상영 순서를 계산해 API 전용 숫자 ID를 만든다.
- `GET /api/movies`와 `POST /api/reservations`는 같은 계산 규칙을 사용해 상영을 조회한다.

### 3. 예매 처리 흐름
1. 데이터베이스에서 최신 `MovieTheater`를 조회한다.
2. 요청의 `screeningId`와 좌석 문자열을 도메인 상영과 좌석 좌표로 변환한다.
3. 기존 `Cart`, `Receipt`, `PaymentController`, 할인 정책을 사용해 총 결제 금액을 계산한다.
4. 결제를 확정한 뒤 예매 정보를 데이터베이스에 저장한다.
5. 예매 결과를 HTTP 응답 DTO로 변환한다.

### 4. 오류 응답 전략
- 존재하지 않는 상영: `404 Not Found`
- 이미 예약된 좌석: `409 Conflict`
- 잘못된 좌석 형식, 결제 수단, 포인트 입력: `400 Bad Request`
- 오류 본문은 `message` 필드 하나를 갖는 JSON으로 반환한다.

## AI 활용 기록
- AI를 사용해 HTTP API 계층을 설계할 때 기존 도메인 변경을 최소화하는 방향을 먼저 검토했다.
- 제안된 코드나 구조는 그대로 복사하지 않고, 현재 프로젝트의 문자열 ID 전략, JDBC 저장 구조, 기존 할인 정책에 맞게 다시 수정했다.
- 이번 단계에서 학습한 내용:
  - 스프링 부트 애플리케이션 진입점과 REST 컨트롤러 구성 방법
  - 도메인 모델과 HTTP DTO를 분리하는 이유
  - HTTP 상태 코드(`200`, `201`, `400`, `404`, `409`)를 기능에 맞게 선택하는 기준
